# ADR-0007. Протокол офлайн-синхронизации: change feed + идемпотентный push

- Дата: 2026-10-27
- Статус: Accepted

## Контекст

Курьер работает в зонах без связи: меняет статусы, фиксирует доставку, фото, тару. Часть 6 `full-spec.md` задаёт требования, но не фиксирует механизм курсора, идемпотентности и разрешения конфликтов. Ошибка здесь — главный риск переписывания (roadmap, риск 1), поэтому протокол проверен спайком до начала MAUI.

## Решение

1. **Delta pull — серверный change feed.** Таблица `SYNC_CHANGE`: каждое изменение домена добавляет запись с монотонным `Id` (long). `Id` — **непрозрачный курсор**: клиент передаёт `since`, сервер возвращает `changes`, `nextCursor`, `hasMore`. Время (`UpdatedAt`) курсором не является — часы клиента/сервера и одинаковые timestamps ломают выборку.
2. **Push — журнал операций.** Таблица `SYNC_OPERATION` с UNIQUE `(TenantId, ClientOperationId)`. Повтор операции возвращает сохранённый результат с `isDuplicate = true` и не применяет её второй раз. Каждая операция обрабатывается в транзакции: либо состояние + change feed + запись операции, либо ничего.
3. **Конфликты — версия записи.** У `ORDER` есть `Version` (long). Клиент присылает `ExpectedVersion`; при несовпадении сервер возвращает `Conflict` и актуальный снапшот, состояние не меняется (server-wins).
4. **Tombstones.** Удаление сущности обязано писать `SYNC_CHANGE` с `ChangeType = Tombstone`; клиент удаляет запись локально. В спайке — `ISyncService.AppendTombstoneAsync` (будет вызываться доменными операциями удаления).
5. **Результат операции:** `Applied | Rejected | Conflict` + машиночитаемые ошибки (`order_not_found`, `invalid_transition`, `version_conflict`, `invalid_payload`, `unsupported_operation`).
6. **Порядок.** Клиент отправляет родитель → потомок. Сервер применяет операции батча последовательно; при ошибке предыдущие остаются применёнными (каждая операция атомарна отдельно).
7. **Источник изменений.** Change feed пополняется и sync-операциями, и приёмом заказов из amoCRM (создание/обновление/отмена). Иначе курьер не увидит новые назначения.

## Последствия

- Плюсы: нет зависимости от часов, безопасные ретраи, явные конфликты, простое масштабирование pull.
- Минусы: `SYNC_CHANGE` растёт — нужна ретенция/компакция; `Version` нужно увеличивать дисциплинированно (пока вручную); курсор привязан к тенанту.
- В спайке реализована одна операция — `SetOrderStatus`. Доставка, фото и тара добавляются по той же схеме.
- `Version++` вручную — временно; далее EF concurrency token или interceptor.

## Проверка

- 7 новых тестов: идемпотентность, конфликт версий, запрещённый переход, delta pull с tombstone, пагинация, изоляция тенантов, запись change feed из intake. Всего 16/16 зелёных.
- Ручной смоук: `POST /api/sync/push` (Applied), повтор (Duplicate), `GET /api/sync/pull` (2 изменения, курсор 2), статус заказа `Accepted`, версия 2.

## Что дальше

- Заменить ручной `Version++` на EF concurrency token.
- Ретенция/компакция `SYNC_CHANGE`, снапшоты для холодного старта.
- `USER_DEVICE.LastSeenAt` + уведомление «офлайн > N».
- Auth, tenant-resolving, привязка операций к устройству и пользователю.
